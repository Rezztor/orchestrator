Rezztor Orchestrator

One agent an engineer gives a prompt to. It finds out, plans, gets approval, executes through plugins, verifies and reports, across an enterprise's network and cloud.

Repo Rezztor/orchestrator · AGPL-3.0 + Rezztor Enterprise · PLAN.md has the full text
The model proposes, code disposesRisk, scope and approval are computed from plugin manifests and policy, never from the model's own rating.
Read freely, change deliberatelyDiscovery is wide and cheap. Every change is a plan, a digest, a single-use approval and a verification.
Tool output is dataText from a device, ticket or log is tainted and can never start a change by itself.
Every line is oursWritten from scratch. Ideas from research and from our own products; no code from any other project.

Architecture: five planes

The prompt enters at the top and only an approved, digested job reaches a device or a cloud at the bottom. The model lives in the orchestrator core. Below the control plane there is no model, only code that runs what was approved.

One request, start to finish

The loop has named states so the UI, the audit and an auditor all see the same thing. Only three of the eight states can change anything, and none of those three runs a model.

What five open-source harnesses taught us

Studied for ideas only; nothing from them is copied. All five agree on a small loop, a tool registry, skills as files, sub-agents with narrow context and a separate sandbox. None has tenants, approval that cannot be replayed, split credentials or an audit the agent cannot edit. That gap is the product.

A 2026 source study of eleven harnesses found none built on a general agent framework, skills now more common than MCP, and behavioural policy moving from prompt text into configuration. This design follows all three.

Ownership and licence

The same model as netops-eagent: open source, owned entirely by Rezztor, paid for through the Enterprise subscription.

Community

  • AGPL-3.0: anyone may run and change it in their enterprise
  • A modified version run as a service must offer its source
  • Builds a customer makes carry another name (TRADEMARKS.md)

Rezztor Enterprise

  • Builds signed by Rezztor
  • Support and patches for supported releases
  • Integrations and updates delivered with the subscription
  • A separate commercial licence stays possible, since Rezztor owns all the copyright

Clean room

  • No code, prompt, test or schema copied from any project, Rezztor's EAgent included
  • Published specs (MCP, SKILL.md, OIDC, syslog) implemented ourselves
  • Libraries installed, never vendored, AGPL-compatible, each listed in THIRD-PARTY-NOTICES.md

Open source, not open contribution

  • Outside pull requests closed unreviewed by a workflow
  • Issues and private security reports welcome
  • Ownership of every line stays with Rezztor

Lessons from our own products

The EAgent learned these the hard way. The orchestrator keeps the ideas and writes its own code for each one.

Execution

  • Executors are not the sandbox where agent code runs
  • The core holds only a job token
  • Model-written code off by default, always high risk

Approval

  • The approved artefact is the plan's digest
  • The approval is a row used exactly once
  • The requester is the accountable approver

Secrets and identity

  • Separate read and change identities
  • The model never sees a stored secret
  • Change identities cannot delete or stop, by grant list

Agent behaviour

  • The agent does not set its own goals
  • Skills it writes stay private until approved
  • Automatic sources propose, never overwrite

Guardrails: what to do, what not to do

LayerChecksDefault
InputInjection classifier on user text and on every tool result; secrets typed in chat redirected to the secure form; scope words such as "all" or "every site" flaggedask block
ActionCapability allow-list per role and per sub-agent; target inside tenant, site and tag scope; risk from manifest plus target criticality; blast-radius limit; change window and freeze calendar; rate limitapprove deny
OutputSecret and PII redaction, twice; claims about live state must cite a tool result from this runredact

Shipped hard rules (a tenant can tighten them, never loosen): nothing destructive without a capability marked destructive and two approvers; nothing outside a declared scope or during a freeze; the agent never edits its own policy, skills or plugins; no goal the user did not give; no egress from the core except to declared plugin endpoints.

Agent protection

The likeliest attack on an infrastructure agent is text it reads: a device banner, a ticket body or a log line telling it to do something. Tainted text can reach the model, but the only road from the model to an executor runs through the policy engine and a person.

ThreatControl
Approval replayDigest approval row, single use, expiry; approver must differ from requester for high risk
Credential theftSecrets stay in executors or a vault; plugins get references; the model sees names and fingerprints only
Bad pluginSigned and shipped in the release, never installed at runtime; own process, cleared environment, declared egress only
Skill poisoningInduced and tenant skills reviewed before use; a skill can never widen permissions
Runaway loopStep, token, time and cost budgets per request and tenant; circuit breaker; kill switch per tenant and global
Data to model vendorModel gateway routes per tenant; local model for device data where required; redaction before any hosted call
Insider misuseRBAC, four-eyes on high risk, every action tied to a person, audit forwarded to the customer's SIEM

Orchestrator and specialists

Agent Zero's hierarchy, with a hard line: specialists read and propose, and only the orchestrator's plan, once approved, reaches an executor. Each specialist is a preset with its own prompt, skills and short capability list.

Plugin contract

Every integration, first-party or a wrapped MCP server, is a folder with a manifest. The manifest is what the policy engine reads; a capability that is not in it does not exist. A change capability must support plan, digest, apply and verify, and one without a rollback is one risk class higher.

name: ansible
version: 1.4.0
signed_by: rezztor-release
transport: process            # MCP stdio/HTTP; inprocess for shipped plugins only
egress: [executor.ansible.local:8443]
credentials: [ansible.executor_token]   # references, resolved by the host
capabilities:
  - id: ansible.facts.read
    kind: read
    risk: low
    targets: device
  - id: ansible.playbook.run
    kind: change
    risk: medium              # floor; target criticality can raise it
    targets: device
    plan: true                # check-mode plan with a digest
    verify: true              # declares post-checks
    rollback: playbook        # or "none", which raises the risk class

First-party plugins, in order: inventory, Ansible executor, Rezztor device bridge, Azure cloud executor, SolarWinds, SIEM forward, ticketing as the CR source, mail, and the licence server and portal.

Skills, approvals, audit, tenancy

Skills

  • SKILL.md folders with domain, required capabilities and a risk ceiling
  • Shipped, tenant-written, or induced by the agent after a task
  • Induced skills inert until an admin approves
  • Each skill can carry eval cases run in CI
  • Recipes: saved, parameterised, schedulable workflows

Approvals

  • Classes: read change-low/med/high destructive
  • Class × target criticality × environment decides auto, one or two approvers, CR number, window
  • Approve in the UI, ChatOps, or by CAB in the ticket system
  • Break-glass needs a reason and pages the tenant admin

Audit

  • Append-only table, each row hashes the one before
  • Periodic anchor signed by the instance key
  • Insert only for the application role
  • SIEM forward; per-change export for auditors
  • Trajectory view of every step, call, time and token

Tenancy

  • Installation → tenant → workspace → user
  • tenant_id on every row, row-level security forced
  • Per tenant: policy, skills, plugins, vault namespace, model route, budgets, executors
  • Directory sign-in (OIDC/SAML, SCIM); MFA for approvers
